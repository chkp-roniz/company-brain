# Company Brain — Requirements

**Normative.** This document states what a Company Brain must do. It is written for any organization that wants to build one. It contains no organization-specific names, hosts, or data.

Conventions:

- **MUST / MUST NOT / SHOULD / MAY** follow RFC 2119.
- Requirement IDs are stable: `REQ-<AREA>-<nn>`. Areas: `OBJ` objective, `IN` input, `PR` processing, `ME` memory, `EV` evaluation, `OUT` output, `SC` scope and promotion, `GOV` governance, `SEC` security, `NFR` non-functional. Acceptance scenarios: `AS-nn`. Open decisions: `OD-nn`.
- Component numbers `[1]`–`[10]` refer to the logical architecture in [03-architecture.md](03-architecture.md) [§3](03-architecture.md#3-logical-architecture).
- Diagrams are plain ASCII. Read them in a monospace font.

Related documents: [02-functionality.md](02-functionality.md) (how the system behaves), [03-architecture.md](03-architecture.md) (how it is built), [04-kpi-and-measurements.md](04-kpi-and-measurements.md) (how it is measured).

## 1. Objective

| ID | Requirement |
|---|---|
| <a id="req-obj-01"></a>REQ-OBJ-01 | The system MUST capture experience created during real work, convert it into governed memory units, and deliver the minimum sufficient context to the right person or agent at the right moment. |
| <a id="req-obj-02"></a>REQ-OBJ-02 | The system distributes **experience** (how outcomes were reached and what was learned), not merely documents. Making existing documents searchable does not satisfy this objective. |

```
   +-------------------------------------+     +-------------------------------------+
   |  ORGANIZATIONAL KNOWLEDGE           |     |  ORGANIZATIONAL EXPERIENCE          |
   |  what the organization knows or     |     |  what the organization learned on   |
   |  has already decided                |     |  the way to the result              |
   |                                     |     |                                     |
   |  documents, databases, code,        |     |  what was tried, what failed, what  |
   |  tickets, procedures, policies      |     |  was fixed, why a decision changed, |
   |  kept by systems of record          |     |  which exception appeared, what     |
   |                                     |     |  worked only in one context         |
   |  = the RESULT                       |     |  = the PATH to the result           |
   +-------------------------------------+     +-------------------------------------+
   a warehouse makes this searchable           the Company Brain must also remember this
```

## 2. Non-goals

The system is **not**:

- a connector layer over enterprise documents
- a single vector database containing all organizational content
- a chat interface over systems of record
- a mechanism that injects the entire "company brain" into every prompt
- an autonomous policy author
- a replacement for authoritative source systems
- tied to one model, agent, or harness

A proposal that satisfies the requirements by building one of the above has misread them.

## 3. Functional model

Four functions. Governance is a cross-cutting control plane, not a fifth step. What happens after output returns as new input.

```
               +---------------------------------------------------------+
               | GOVERNANCE CONTROL PLANE (cross-cutting; not a 5th step)|
               | identity . permissions . policy precedence . audit trail|
               | expiry . deletion . rollback . scope control            |
               +----+---------------+---------------+--------------+-----+
                    |               |               |              |
                    v               v               v              v
 work trails   +----------+   +------------+   +----------+   +----------+   minimum sufficient
 systems of -->|  INPUT   |-->| PROCESSING |-->|  MEMORY  |-->|  OUTPUT  |--> context to the right
 record        +----------+   +------------+   +----------+   +----------+   person or agent, in-tool
                    ^                                              |
                    |          outcome of the output               |
                    |   (helped / misled / ignored / corrected)    |
                    +-------------  returns as new input  ---------+
```

| Function or concern | One-line responsibility | Components |
|---|---|---|
| Input | Capture official knowledge and work trails as immutable evidence and trajectories | [1] [2] |
| Processing | Turn trajectories into candidate experience units with evidence links and usage bounds | [3] |
| Memory | Decide what to retain, in what form, for how long, for whom, and when to stop trusting it | [4] [5] |
| Output | Deliver the smallest useful set of memory, in-tool, before the model reasons, with provenance | [6] [7] [8] |
| Governance | Identity, permissions, policy precedence, audit, expiry, rollback across all four | [9] |
| Evaluation | Connect delivered memory to observed outcomes; feed back as input | [10] |

## 4. Actors

| Actor | Role in the system |
|---|---|
| Worker (engineer, analyst, researcher) | Produces work trails as a by-product of normal work; receives context inside their tools; may own personal-scope memory. |
| AI agent / automation | Produces trajectories; consumes injected context; may explore memory through tools; never writes shared memory directly. |
| Memory owner | Accountable for a memory unit or a scope (team, product, organization); approves scope changes; resolves contradictions. |
| Policy owner | Human owner of policy objects. The only actor who may change policy. |
| Platform administrator | Operates adapters, admission rules, retention defaults, audit, and rollback. |
| Security / compliance reviewer | Audits provenance, access, and leakage controls. |

## 5. Functional requirements

### 5.1 Input — capture (components [1], [2])

The unit of capture is a trajectory, not a document and not a session summary.

```
  +---------+    +---------+    +---------+    +------------+    +---------+
  | problem |--->| attempt |--->| mistake |--->| correction |--->| outcome |
  +---------+    +---------+    +---------+    +------------+    +---------+
       |              |              |               |                |
       +--------------+--------------+---------------+----------------+
                                     |
                      one TRAJECTORY = an ordered sequence of evidence events
                      (the unit of capture; stored immutably; never rewritten)
```

| ID | Level | Requirement |
|---|---|---|
| <a id="req-in-01"></a>REQ-IN-01 | MUST | Ingest official knowledge from systems of record: documents, databases, code, tickets, procedures, and policies. |
| <a id="req-in-02"></a>REQ-IN-02 | MUST | Ingest work trails: agent and coding-tool sessions, conversations, user corrections and feedback, tool calls and their results, code reviews, decisions and changes of direction, failed attempts, retries, and actual outcomes. |
| <a id="req-in-03"></a>REQ-IN-03 | MUST | Capture trajectories (problem → attempt → mistake → correction → outcome), preserving event order, timestamps, actor identity, and the links between events of the same piece of work. |
| <a id="req-in-04"></a>REQ-IN-04 | SHOULD | Capture passively, as a by-product of the tools in which work already happens. |
| <a id="req-in-05"></a>REQ-IN-05 | MUST NOT | Depend on employees maintaining another knowledge repository, writing post-hoc documentation, or tagging content in order for the system to learn. |
| <a id="req-in-06"></a>REQ-IN-06 | MUST | Store captured material as immutable evidence in [2]. Evidence becomes a managed memory unit only after processing and admission; capture alone never creates memory. |
| <a id="req-in-07"></a>REQ-IN-07 | MUST | Capture only what the owning identity and applicable policy permit ([REQ-GOV-03](#req-gov-03)), and record what was captured, from where, and under which authorization. |
| <a id="req-in-08"></a>REQ-IN-08 | SHOULD | Be extensible by adapter to work surfaces beyond software development: query history, notebooks, BI tools and dashboard changes, research tools, analyst and researcher agent sessions. Experience created in ad hoc analytical work must not be lost. |

#### 5.1.1 Principles for observed work

Observation-based capture (a harness recording an agent session, or a recorder observing an employee's screen, terminal, and narration) is the richest input the system has and the most sensitive. These principles apply to every observation-based adapter, from the first harness hooks to a screen-level recorder.

| ID | Level | Requirement |
|---|---|---|
| <a id="req-in-09"></a>REQ-IN-09 | MUST | Observe real work rather than rely on employees to document it from memory. Where a surface can be observed (screen, window and application switches, pages visited, clipboard previews, terminal commands and output, tool calls and results, optional spoken narration), capture the observation as evidence. Recording is visible to the observed employee, who can pause, stop, or discard a session at any time. |
| <a id="req-in-10"></a>REQ-IN-10 | MUST | Reconstruct intent and ordered steps from several evidence sources combined, not from a single stream. Every reconstructed step records which evidence events support it and from which sources. A step with no supporting evidence is marked as inferred. |
| <a id="req-in-11"></a>REQ-IN-11 | MUST | Keep raw evidence separate from its interpretation. The reconstruction (intent plus steps) is an interpretation object stored beside the evidence and linked to it. It never replaces, edits, or summarizes away the raw evidence, which stays available for inspection (L2). |
| <a id="req-in-12"></a>REQ-IN-12 | MUST | Let the observed employee review the reconstruction before it becomes a candidate: correct steps, redact content, or reject the session. The review decision and edits are recorded as evidence events. Review is neither admission, nor policy clearance, nor a security guarantee. |
| <a id="req-in-13"></a>REQ-IN-13 | MUST | Build privacy, provenance, verification, and outcome feedback into the capture pipeline itself: (a) notice to the employee before every recording and employee control over the session; (b) on-device detection and redaction of secrets and personal data before anything leaves the workstation; (c) provenance stamps (actor, time, source, authorization) on every event; (d) recorded verification results (which checks ran on the reconstruction and what they found); (e) an outcome channel that links later results back to the capture ([REQ-EV-10](#req-ev-10)). None of these may be added after the fact. |
| <a id="req-in-14"></a>REQ-IN-14 | MUST | Keep observed-work data inside organization-controlled systems. Reconstruction and any model-based analysis run only through approved endpoints ([REQ-SEC-08](#req-sec-08), [REQ-SEC-09](#req-sec-09)). Recording data is never sent to a third-party cloud for analysis. Rollout beyond consenting pilot users is subject to the organization's privacy and legal review for monitoring of employee activity. |

#### 5.1.2 Sources and portability

| ID | Level | Requirement |
|---|---|---|
| <a id="req-in-15"></a>REQ-IN-15 | MUST | Treat code graphs (symbols, call and dependency relations, ownership, and version history derived from repositories) as a system-of-record source alongside the code itself ([REQ-IN-01](#req-in-01)). Every entity and relation taken from a code graph records the repository, commit, and graph-builder version it came from, so it can be re-derived and invalidated when the code changes. A code graph describes the code; it never replaces the code as the authority. Entity identity follows [03-architecture.md](03-architecture.md) [§7.1](03-architecture.md#71-semantic-identity-and-relationship-typing). |
| <a id="req-in-16"></a>REQ-IN-16 | MUST | Support import and export of memory in portable structured formats, including structured Markdown memory files and similar formats used by other memory systems. Import: provenance of the source (system, file, author, time, original identifiers) is preserved on every imported item, and imported items enter as candidates through admission ([4], [REQ-PR-10](#req-pr-10)); they are never admitted directly as memory ([REQ-IN-06](#req-in-06)). Export: only content the requesting identity may see is exported ([REQ-GOV-03](#req-gov-03), [REQ-SC-04](#req-sc-04)); each exported item carries provenance, scope, version, and classification; exports go only to organization-controlled destinations ([REQ-SEC-09](#req-sec-09)). Formats are documented and versioned so that memory is never coupled to one tool ([REQ-NFR-06](#req-nfr-06)). The managed store stays canonical; an export is a derived view. |

### 5.2 Processing — reflection and extraction (component [3])

| ID | Level | Requirement |
|---|---|---|
| <a id="req-pr-01"></a>REQ-PR-01 | MUST | Transform raw activity into candidate experience units. Indexing, chunking, and summarization alone do not satisfy this requirement. |
| <a id="req-pr-02"></a>REQ-PR-02 | MUST | Extract: new facts; decisions together with their reasons; mistakes, corrections, and candidate lessons; recurring patterns; solutions that hold only in a specific context. |
| <a id="req-pr-03"></a>REQ-PR-03 | MUST | Distinguish evidence from interpretation, and classify every output as one of: evidence, interpretation, lesson (experience), durable knowledge, skill candidate, policy reference, authoritative reference. |
| <a id="req-pr-04"></a>REQ-PR-04 | MUST | Preserve a link from every candidate to the originating trajectory and supporting evidence events. |
| <a id="req-pr-05"></a>REQ-PR-05 | MUST | Identify duplicates and merge them without removing meaningful contextual differences. |
| <a id="req-pr-06"></a>REQ-PR-06 | MUST | Surface contradictions between a candidate and existing memory. Contradictions are recorded and routed, never silently resolved. |
| <a id="req-pr-07"></a>REQ-PR-07 | MUST | Identify the conditions under which a lesson applies (usage bounds: context, audience, tool, version, environment). |
| <a id="req-pr-08"></a>REQ-PR-08 | MUST | Produce experience units with source, context, confidence, and usage bounds, not session summaries. |
| <a id="req-pr-09"></a>REQ-PR-09 | MUST | Keep execution, reflection, curation, and admission as separable responsibilities. The executing agent MUST NOT have authority to write directly to shared organizational memory. |
| <a id="req-pr-10"></a>REQ-PR-10 | MUST | Normalize and classify sensitive content before any candidate is considered for admission ([REQ-GOV-10](#req-gov-10), [§7](#7-security-and-compliance-baseline)). |
| <a id="req-pr-11"></a>REQ-PR-11 | MUST | Detect meaningful boundaries (completion, failure, correction, decision) and use them to trigger reflection, rather than reflecting on every event. |
| <a id="req-pr-12"></a>REQ-PR-12 | MAY | Run the write path asynchronously. It MUST optimize for evidence quality and safe admission, not latency. |
| <a id="req-pr-13"></a>REQ-PR-13 | MUST | Generalize reconstructed procedures toward native tools. When a reconstruction becomes a Skill Candidate, express steps by intent and prefer the executing agent's native tools (CLIs, APIs, connectors) over replaying UI coordinates or clicks; parameterize the single observed case into a general procedure; mark steps that could not be generalized and remain UI-bound. |
| <a id="req-pr-14"></a>REQ-PR-14 | MUST | Classify every artifact produced from observed work as an Experience unit or a Skill Candidate, never directly as a Skill, durable knowledge, or policy ([REQ-PR-03](#req-pr-03), [REQ-ME-03](#req-me-03)). |
| <a id="req-pr-15"></a>REQ-PR-15 | MUST | Build a decision-lineage chain from trajectory evidence: a **Proposal** (what was suggested, and by which person or agent), a **Decision** (what an authorized actor selected), an **Execution** (what actually ran, and under which identity), and an **Outcome** (what was later observed). Memory unit versions supplied when the Proposal was made are linked as `informed_by`: this records exposure, not authorship or causation. A Proposal MAY also link to the Context Delivery Receipt that preceded it as `informed_by_receipt` ([REQ-OUT-19](#req-out-19)); that edge likewise records exposure only and MUST NOT be treated as influence or causation. Create and link each record only when the evidence supports that stage; a stage without evidence stays unknown and is never inferred. A proposal that was not selected stays in history and is never recorded as the decision taken. |
| <a id="req-pr-16"></a>REQ-PR-16 | MUST | Preserve the speech-act class of every captured input and of every processing output that enters admission. Distinguish at least: question; request; proposal; assertion; commitment; agent report; observed event; verified outcome. A question is not a fact. A request is not a commitment. An agent report is not proof of execution. Silence is not proof of completion. Repetition is not independent corroboration. These classifications MUST affect admission, grounding, and promotion; storage or repetition alone MUST NOT raise trust. |

### 5.3 Memory — the core layer (components [4], [5])

| ID | Level | Requirement |
|---|---|---|
| <a id="req-me-01"></a>REQ-ME-01 | MUST | Decide what to retain, in what form, for how long, for whom, and when the organization should stop trusting it. A store that only keeps what was written into it does not satisfy this requirement. |
| <a id="req-me-02"></a>REQ-ME-02 | MUST | Support four memory categories: working memory (current objective, state, constraints, unresolved decisions; lifecycle in [REQ-ME-19…25](#req-me-19) and [REQ-ME-31](#req-me-31)); episodic memory (what happened in a specific task or session); durable knowledge (facts and lessons distilled across experiences); personal context (preferences and working patterns scoped to an individual). |
| <a id="req-me-03"></a>REQ-ME-03 | MUST | Keep skills, policies, and authoritative sources as separate object classes linked to memory, never merged into it. Memories and lessons advise; skills execute; policies constrain and remain human-owned; authoritative sources retain their official status. |
| <a id="req-me-04"></a>REQ-ME-04 | MUST | Carry on every memory unit: unique identity; source and supporting evidence; owner; creation context; confidence; visibility scope; relevance scope; version; freshness and validity; relationships to other units; usage and outcome history; source class; retention and retrieval decisions; and the grounding ceiling with its permitted uses ([REQ-ME-15](#req-me-15)). |
| <a id="req-me-05"></a>REQ-ME-05 | MUST | Support typed relationships: `derived_from`, `supported_by`, `contradicts`, `supersedes`, `relevant_to`, `promoted_from`; and, for decision lineage ([REQ-ME-14](#req-me-14)), `proposed_by` (Proposal → proposer), `informed_by` (Proposal → memory unit versions supplied), `informed_by_receipt` (Proposal → Context Delivery Receipt that preceded it; [REQ-OUT-19](#req-out-19)), `decision_selects` (Decision → Proposal), `decided_by` (Decision → authorized actor), `implements` (Execution → Decision), `executed_by` (Execution → executing identity), `resulted_in` (Execution → Outcome), and `evaluated_by` (Outcome → evaluator). |
| <a id="req-me-06"></a>REQ-ME-06 | MUST | Support the lifecycle transitions promotion, weakening, supersession, archival, expiry, contradiction handling, and rollback ([03-architecture.md](03-architecture.md) [§8](03-architecture.md#8-memory-lifecycle)). |
| <a id="req-me-07"></a>REQ-ME-07 | MUST | Retain several conflicting lessons when each is valid in a different context, each with its own ownership and evidence. MUST NOT force a single global truth. |
| <a id="req-me-08"></a>REQ-ME-08 | MUST | Treat forgetting as removing a unit's influence on current work. Forgetting does not by default delete history; source, versions, and evaluation history are retained for audit. Deletion is a separate governed operation ([REQ-GOV-07](#req-gov-07)). |
| <a id="req-me-09"></a>REQ-ME-09 | MUST | Update memory incrementally: add or change only the affected units. MUST NOT rely on repeated monolithic LLM rewrites of accumulated memory. |
| <a id="req-me-10"></a>REQ-ME-10 | MUST | Prevent a local mistake from becoming organizational truth (promotion gates [§5.6](#56-scope-and-promotion-component-4), evaluation [§5.4](#54-memory-utility-evaluation-component-10)). |
| <a id="req-me-11"></a>REQ-ME-11 | MUST | Preserve previous versions of every unit and support rollback of any change. |
| <a id="req-me-12"></a>REQ-ME-12 | MUST | Keep a Skill Candidate a candidate (not executable in production and not promotable) until all of the following gates have passed and their results are recorded on the candidate: compared with additional examples of the same intent; checked against applicable policy; evaluated on real outcomes in a safe environment, canary, or shadow evaluation ([REQ-EV-08](#req-ev-08), [REQ-EV-13](#req-ev-13)), with evidence across distinct contexts that meets the threshold and no protected regression ([REQ-EV-16](#req-ev-16), [REQ-EV-17](#req-ev-17)); approved by an owner; versioned; made reversible (can be disabled and rolled back). The evidence threshold is configurable by capability class, domain, evidence strength and diversity, risk, and blast radius; no fixed count of contexts or runs applies everywhere. The promotion record states the threshold applied and why it fits the candidate's risk. These are the minimum gates; the full skill compilation, evaluation, and promotion design remains [OD-08](#od-08). |
| <a id="req-me-13"></a>REQ-ME-13 | MUST | Treat evidence that a scope or source is deprecated (an archived repository, a retired product, a superseded procedure) as a lifecycle trigger. Every unit derived from the deprecated scope or source is weakened or expired ([REQ-ME-06](#req-me-06)), with history and evidence preserved ([REQ-ME-08](#req-me-08)), and the owners of the affected units and of the scope are notified. The transition is versioned and reversible by re-validation or rollback ([REQ-ME-11](#req-me-11)). A unit that is also supported by evidence from a source that is not deprecated is weakened and routed to its owner for re-validation rather than expired. |
| <a id="req-me-14"></a>REQ-ME-14 | MUST | Preserve every decision-lineage chain ([REQ-PR-15](#req-pr-15)) as linked, append-only records. Every record carries its actor (proposer, deciding actor, executing identity, or evaluator), the authority under which it acted, its timestamp, and its supporting evidence. Where a Proposal was preceded by a retrieval, the chain MUST retain the `informed_by_receipt` link to that Context Delivery Receipt ([REQ-OUT-19](#req-out-19)) when one exists; the link proves exposure of the delivered representation, not influence or causation. An Outcome also carries its evaluator, the acceptance criterion it was judged against, and its uncertainty. An Outcome is a **Verified outcome** only when an evaluator applied an explicit acceptance criterion; a successful execution alone is not one. A later correction is a new record linked to the original Outcome, which is never overwritten. |
| <a id="req-me-15"></a>REQ-ME-15 | MUST | Make retention, retrieval, and grounding three separate decisions. **Retention**: whether the unit is kept. **Retrieval**: whether it may be returned to a consumer. **Grounding**: whether it may support a factual claim, a recommendation, or a consequential action. Retention and retrieval rules are recorded on the unit, together with a **grounding ceiling**: the highest purpose class the unit may ever ground, and the non-grounding uses it may serve. Grounding for a specific request is decided at read time and recorded in the selection log ([REQ-OUT-08](#req-out-08)), never as a new unit version. Being retained or retrieved never implies grounding eligibility. |
| <a id="req-me-16"></a>REQ-ME-16 | MUST | Decide grounding deterministically at two levels. The **grounding ceiling** is set at admission from source class, supporting evidence, authority, validity, and policy, and is versioned with its reason. The **per-request decision** is made at read time from the ceiling plus freshness, visibility, the requester's identity, the purpose, the task context, the consequence of the action, and policy; it never exceeds the ceiling. Purpose classes are owner-defined (for example: informational answer, recommendation, consequential action). A verified outcome ([REQ-ME-14](#req-me-14)) is one form of supporting evidence. A record that fails integrity verification ([REQ-SEC-16](#req-sec-16)) is not eligible. |
| <a id="req-me-17"></a>REQ-ME-17 | MUST | Classify assistant-generated beliefs, summaries, self-assessments, and prior utterances as **autobiographical memory**, non-grounding by default. It may be retained and retrieved for continuity. It becomes grounding-eligible only through independent supporting evidence (a tool result, a verified outcome, an authoritative reference, or a person's confirmation), recorded as a new version. |
| <a id="req-me-18"></a>REQ-ME-18 | MUST | Keep autobiographical memory distinguishable from facts, policies, authoritative references, and verified outcomes in storage, at delivery, and in every derived view. Repetition is not corroboration: restating, summarizing, copying, or retrieving a claim again never changes its grounding eligibility. |
| <a id="req-me-19"></a>REQ-ME-19 | MUST | Treat working memory as temporary operational state scoped to one session, task, or handoff, with an owner, a scope, and an expiry. It is not shared organizational memory. |
| <a id="req-me-20"></a>REQ-ME-20 | MUST | Before session end, handoff, reset, or compaction, produce a **continuity checkpoint** that identifies the objective, completed work, pending work, unresolved decisions, constraints, dependencies, evidence and authority boundaries, and next actions. The checkpoint is also kept current during the task, so an abrupt end loses little ([REQ-ME-31](#req-me-31)). |
| <a id="req-me-21"></a>REQ-ME-21 | MUST | Keep a continuity checkpoint distinct from durable memory. It is used to resume its own task, is not returned as organizational knowledge, and never causes automatic admission or promotion. Content leaves a checkpoint only through the normal write path ([REQ-PR-09](#req-pr-09), [REQ-SC-02](#req-sc-02)). |
| <a id="req-me-22"></a>REQ-ME-22 | MUST | Make compaction preserve provenance, roles, authority boundaries, unresolved state, evidence links, and grounding status ([REQ-ME-18](#req-me-18)). Deterministic removal of obsolete and duplicate content runs before any semantic summarization. |
| <a id="req-me-23"></a>REQ-ME-23 | MUST | Record for every compaction a **compaction record** of what was retained, removed (and by which rule), transformed, and left uncertain. Uncertainty is stated, never smoothed into a clean summary. |
| <a id="req-me-24"></a>REQ-ME-24 | MUST | Evaluate checkpoints and compaction with resume tests, including tests after abrupt termination, that detect invented state, repeated completed work, and lost constraints. A failed resume test is recorded as evidence ([REQ-IN-02](#req-in-02)). |
| <a id="req-me-25"></a>REQ-ME-25 | MUST NOT | Require a model's hidden reasoning as organizational memory. Preserve decisions, evidence, corrections, and observable outcomes instead. |
| <a id="req-me-26"></a>REQ-ME-26 | MUST | Provide governed memory maintenance that runs on a schedule, when a monitored measure crosses a threshold, and on events, across canonical memory, working memory, and retrieval projections. |
| <a id="req-me-27"></a>REQ-ME-27 | MUST | Monitor at least: growth, retrieval latency, duplicates, contradictions, staleness, expiry, harmful or ignored units, skill drift, changed dependencies (sources, tools, schemas, models), due review dates, and projection inconsistency with canonical memory. |
| <a id="req-me-28"></a>REQ-ME-28 | MUST | Let maintenance propose review, deduplication, weakening, supersession, archival, expiry, invalidation, recomputation, projection repair, or retirement. A proposal names its trigger, evidence, and affected units, and is routed to the owner. |
| <a id="req-me-29"></a>REQ-ME-29 | MUST NOT | Silently rewrite or delete canonical evidence or canonical memory during maintenance. Every maintenance action records its trigger, evidence, owner, acting identity, prior version, expected version, idempotency key, reason, time, and rollback path ([REQ-ME-08](#req-me-08), [REQ-ME-09](#req-me-09), [REQ-ME-32](#req-me-32)). |
| <a id="req-me-30"></a>REQ-ME-30 | MUST | Execute automatically only operations on a predefined, owner-approved list of low-risk, reversible maintenance actions (for example, rebuilding a stale projection or expiring working memory past its expiry). Every other action becomes a governed proposal decided by an owner through admission or governance. A failed automatic action is rolled back and shown to the owner. Each entry on the list is an action class with a named owner ([REQ-ME-34](#req-me-34)), and no automatic action overrides a legal hold or retention obligation ([REQ-ME-33](#req-me-33)). |
| <a id="req-me-31"></a>REQ-ME-31 | MUST | Keep continuity safe against abrupt termination (crash, kill, lost connection), when no end-of-session trigger runs. Update the continuity checkpoint incrementally after each material state change and periodically, and record its age. Journal every irreversible or externally visible action before it runs (intent and an idempotency key) and after it (result). On resume after an abrupt end, reconcile the latest checkpoint and the journal with external state: an action with an intent but no recorded result is unknown and is checked, never re-run blindly. The maximum acceptable state loss (recovery point) is set per task class. |
| <a id="req-me-32"></a>REQ-ME-32 | MUST | Make maintenance safe under concurrency. Every automatic action and every proposal names the expected version of each unit it changes, and is committed only if that version is still current; otherwise it is rejected as stale and re-evaluated. Every action carries an idempotency key, so a retry never applies it twice. Conflicting actions on the same unit are serialized. |
| <a id="req-me-33"></a>REQ-ME-33 | MUST | Apply a fixed precedence to maintenance: legal hold, then retention and deletion obligations ([REQ-GOV-07](#req-gov-07), [REQ-SEC-15](#req-sec-15)), then owner decisions, then automatic maintenance. A unit or evidence record under legal hold is never expired, archived, merged away, or deleted by maintenance. A retention or deletion obligation is never blocked or delayed by maintenance. A conflict is blocked and routed to the policy owner. |
| <a id="req-me-34"></a>REQ-ME-34 | MUST | Give every maintenance action class (for example, projection repair, working-memory expiry, deduplication, archival) a named owner who approves whether it is on the low-risk list, its scope, and its conditions. A proposal is routed to the owner of each affected unit. When an action class owner and a unit owner disagree, the action does not run and the conflict is routed through governance. |
| <a id="req-me-35"></a>REQ-ME-35 | MUST | Keep references working after deduplication, merge, supersession, and archival. The merged-away or superseded unit stays as a redirect to its successor with its history ([REQ-ME-08](#req-me-08)). Links, dependent units and skills, selection logs, and evaluation records still resolve, and dependents are flagged for review through the dependency walk ([REQ-ME-13](#req-me-13)). |

### 5.4 Memory utility evaluation (component [10])

Validity (the unit is well supported) and utility (supplying it improved outcomes) are different properties and are measured separately.

| ID | Level | Requirement |
|---|---|---|
| <a id="req-ev-01"></a>REQ-EV-01 | MUST | Evaluate memory validity and memory utility separately. A unit may be well supported by evidence yet provide no measurable benefit in a given context. |
| <a id="req-ev-02"></a>REQ-EV-02 | MUST | Treat candidate and admitted units as hypotheses whose utility is demonstrated through downstream outcomes, not assumed from confidence, retrieval frequency, or popularity. |
| <a id="req-ev-03"></a>REQ-EV-03 | MUST | Scope utility measurements to the specific memory version, task class, audience, model, harness, and operating context. |
| <a id="req-ev-04"></a>REQ-EV-04 | MUST | Prevent new or materially changed versions from inheriting the utility history of previous versions. |
| <a id="req-ev-05"></a>REQ-EV-05 | MUST | Record beneficial, harmful, ignored, and corrected outcomes. |
| <a id="req-ev-06"></a>REQ-EV-06 | MUST | Record the complete set of memories supplied to a run, and MUST NOT assign the full outcome to every retrieved unit. Attribution separates three levels: **exposure** (the unit version was supplied), **influence** (evidence shows it was used, for example cited, applied, or reflected in a Proposal or Decision), and **causal evidence** (a controlled comparison such as an A/B arm, shadow run, or replay shows the result changes with and without it). Exposure alone earns no credit or blame beyond weak evidence; credit or blame needs influence; a causal claim needs causal evidence. Each attribution records its level and confidence. An outcome with no evidence of influence stays unattributed. |
| <a id="req-ev-07"></a>REQ-EV-07 | MUST | Preserve evaluation history and supporting evidence after a unit is weakened or removed from retrieval. |
| <a id="req-ev-08"></a>REQ-EV-08 | MUST | Restrict evaluation of unvalidated memories to safe environments, controlled canaries, or low-risk tasks. |
| <a id="req-ev-09"></a>REQ-EV-09 | MUST NOT | Weaken mandatory policy or security controls for evaluation purposes. |
| <a id="req-ev-10"></a>REQ-EV-10 | MUST | Record whether retrieved memory helped, misled, was ignored, or required correction. That record becomes new input ([REQ-IN-02](#req-in-02)). |
| <a id="req-ev-11"></a>REQ-EV-11 | SHOULD | Capture outcome signals both implicitly (subsequent corrections, retries, reverts, failed checks) and explicitly (consumer-reported feedback through the tool interface). |
| <a id="req-ev-12"></a>REQ-EV-12 | MUST | Maintain an evaluation protocol that compares the context the Brain supplies with the report of a from-scratch internal research agent for a defined task class. The baseline agent receives the same objective, runs on approved endpoints ([REQ-SEC-08](#req-sec-08)), and has no access to the Brain. Both arms are judged on quality against the actual outcome (not on how convincing the report reads), on tokens spent, and on latency. For each task class the Brain MUST beat or match the baseline on quality while costing less in tokens and latency. Where it does not, the units supplied for that task class become candidates for weakening ([REQ-EV-02](#req-ev-02), [REQ-ME-06](#req-me-06)). The protocol defines the task classes, the judging method, the sample size, and the re-run cadence, and follows [REQ-EV-08](#req-ev-08) and [REQ-EV-09](#req-ev-09). |
| <a id="req-ev-13"></a>REQ-EV-13 | MUST | Support **shadow evaluation** for candidate skills, rules, procedures, and material memory-policy changes. A shadow candidate runs beside the active path on live or replayed work; its output is recorded but never controls a production result, action, or delivered context. |
| <a id="req-ev-14"></a>REQ-EV-14 | MUST | Run every shadow arm on the same **comparison basis** as the active path: the same task identity, authorization boundary, source snapshot, available evidence universe, external-state snapshot, and deterministic filters ([REQ-OUT-06](#req-out-06), [REQ-OUT-18](#req-out-18)). A candidate skill, rule, or procedure receives the same selected context as the active path. A candidate retrieval or memory policy selects its own context from the same evidence universe, because selecting differently is what it is tested for; every arm's selection is logged ([REQ-OUT-08](#req-out-08)). The candidate runs under its own scoped identity, gets no more access than the active path, and has no write path to shared memory or production systems ([REQ-PR-09](#req-pr-09), [REQ-EV-09](#req-ev-09)). |
| <a id="req-ev-15"></a>REQ-EV-15 | MUST | Compare the shadow candidate with the active path and, where feasible, with a no-candidate baseline, on the same comparison basis ([REQ-EV-14](#req-ev-14)). Judge against verified outcomes ([REQ-ME-14](#req-me-14)) where they exist. |
| <a id="req-ev-16"></a>REQ-EV-16 | MUST | Record for every shadow run: applicability, abstention, agreement or disagreement with the active path, execution validity, verified outcome, and negative transfer. Count evidence by distinct representative contexts; repeated runs on one context or one replay count once. Each comparison records its uncertainty, and a promotion recommendation follows a minimum-evidence decision rule set per capability class ([OD-08](#od-08)). |
| <a id="req-ev-17"></a>REQ-EV-17 | MUST | Keep an owner-defined set of **protected tasks** per capability class. A regression on any protected task blocks promotion even when aggregate performance improves. The block and its evidence are recorded on the candidate. |
| <a id="req-ev-18"></a>REQ-EV-18 | MUST | Isolate shadow runs from side effects. A shadow arm reaches tools only through read-only façades: a mutating call (sending a message, changing a ticket, writing a file, calling a mutating API) is recorded as what the candidate would have done and is never executed. An attempt to reach a mutating path outside the façade is blocked, recorded as a side-effect violation, and stops the run. |
| <a id="req-ev-19"></a>REQ-EV-19 | MUST | Control the conditions of every shadow comparison. Record for each arm the time reference, tool results, model and harness versions, and randomness settings. A replay reuses the recorded tool results and snapshots; a live comparison records any difference between arms. A comparison whose conditions differ in a way that could explain the result is flagged and does not count as promotion evidence. |
| <a id="req-ev-20"></a>REQ-EV-20 | SHOULD | Before implementing a new memory or retrieval capability, establish a starter evaluation protocol: about twenty dated questions drawn from real work; the expected current truth and the stale values that MUST NOT be presented as current; a baseline from fresh sessions without the new capability; a held-out split that is rotated after inspection; comparable agent, model, source snapshot, tool budget, and task conditions; measured answer quality, tool calls, latency, and cost; and human calibration of any model judge. The protocol is a diagnostic starting point, not production certification. Security, privacy, scale, recovery, and verified-outcome gates remain separate ([REQ-EV-08](#req-ev-08), [REQ-EV-09](#req-ev-09), [REQ-EV-12](#req-ev-12)). |

Volume, concurrency, and retention sizing targets are set in Phase 0 ([03-architecture.md](03-architecture.md) [§15](03-architecture.md#15-proposed-delivery-phases--proposal)). |
| <a id="req-nfr-10"></a>REQ-NFR-10 | MUST | **Net value accounting.** Measure the system's own net cost per task class. Cost: the tokens and latency spent by the write path (reflection and curation), by injected context, and by retrieval calls. Benefit: savings from shorter sessions, fewer retries, less re-research, and fewer repeated mistakes, together with the change in outcome quality. Token savings alone are not the metric. Measure with an A/B or paired protocol (comparable work with and without Brain-supplied context), and report per scope and per memory version ([REQ-EV-03](#req-ev-03), [REQ-EV-04](#req-ev-04)). Withholding context for measurement never withholds policy or authoritative memory ([REQ-EV-09](#req-ev-09), [REQ-OUT-13](#req-out-13)). A task class whose net value is not positive is reported to its owner, and the units supplied for it become candidates for weakening. |
| <a id="req-nfr-11"></a>REQ-NFR-11 | MUST | **Management dashboard.** Provide a visual dashboard of the critical parts of the solution for memory owners, platform administrators, and security and compliance reviewers. It MUST show at least: (a) users and agents: active counts, scopes held, capture and consumption activity; (b) memories: counts by class, category, scope, and lifecycle state, the admission queue, promotions, and weakened, archived, and expired units; (c) relations: the typed relationships between units ([REQ-ME-05](#req-me-05)), including contradictions, supersessions, cross-scope links, and the path from a unit to its evidence; (d) statistics: capture volume, admission rate, retrieval latency, selection size against budget, and outcome signals (helped, misled, ignored, corrected); (e) net value per task class ([REQ-NFR-10](#req-nfr-10)) and research-agent baseline results ([REQ-EV-12](#req-ev-12)); (f) health and pending work: adapter status, projection staleness, policy conflicts, deprecation notices, open contradictions, pending owner actions, maintenance backlog, stale-action rejections, and legal-hold conflicts ([REQ-ME-26…35](#req-me-26)); (g) trust and learning: grounding status (ceiling coverage, per-request decisions, ceiling breaches; [REQ-ME-16](#req-me-16)), continuity health (resume and crash-resume failures, checkpoint age; [REQ-ME-24](#req-me-24), [REQ-ME-31](#req-me-31)), shadow evaluation (candidates in shadow, promotion decisions and their evidence, side-effect violations; [REQ-EV-13…19](#req-ev-13)), and integrity incidents (failed verification, quarantined records, compromise exposure, unverifiable history; [REQ-SEC-16…19](#req-sec-16)). The dashboard authenticates every request and enforces authorization server-side ([REQ-SEC-01](#req-sec-01)); it shows only what the viewing identity may see ([REQ-SC-04](#req-sc-04), [REQ-GOV-03](#req-gov-03)); it shows identifiers and aggregates, never raw evidence or memory content, unless the viewer drills down to L2 where permitted ([REQ-SEC-07](#req-sec-07)); and actions taken from it (approve, promote, resolve a contradiction, roll back) run through the admission and governance workflows [4] and [9], never around them. |

## 11. Glossary

| Term | Meaning |
|---|---|
| **Company Brain** | The whole system: capture → processing → governed memory → budgeted context delivery, with a feedback loop from outcomes. |
| **Evidence event** | An immutable source record: a message, tool call and result, decision, correction, review comment, outcome. Never rewritten. |
| **Trajectory** | An ordered sequence of evidence events describing one piece of work over time: problem → attempt → mistake → correction → outcome. The unit of capture. |
| **Experience unit** | A contextual lesson inferred from one or more trajectories, with source, confidence, usage bounds, owner, and scope. The primary managed memory object. |
| **Durable knowledge** | A claim supported across sufficient evidence and contexts, distilled from experience. |
| **Skill** | An executable capability with its own validation, versioning, and rollout lifecycle. Separate from memory; linked to it. |
| **Skill Candidate** | A generalized procedure derived from observed work that has not yet passed the gates to become a Skill. Not executable in production. |
| **Policy** | A human-owned, authoritative constraint. Never authored by the system. Takes precedence over local approval. |
| **Authoritative reference** | A pointer to the official source of truth (a system of record). Memory never replaces it. |
| **Managed memory unit** | Any admitted, versioned, owned, scoped unit in the memory store: experience units, durable knowledge, episodic records, personal context. |
| **Memory categories** | Working, episodic, durable knowledge, personal context. |
| **Admission** | The governed step that turns a candidate produced by processing into a managed memory unit. Separate from execution and reflection. |
| **Scope** | The audience a unit is admitted for: personal → team → product → organization. |
| **Promotion** | Widening a unit's scope. Requires evidence, sensitivity handling, ownership, and permission. Repetition alone never promotes. |
| **Visibility vs relevance** | Visibility: who is allowed to access a unit. Relevance: who should receive it for the current task. Modeled separately. |
| **Weakening / supersession / archival / expiry** | Lifecycle transitions that reduce or stop a unit's influence on current work while preserving its history. |
| **Forgetting** | Stopping a unit from influencing work. Not the same as deleting its history. |
| **Utility vs validity** | Validity: the unit is supported by evidence. Utility: supplying it measurably improved outcomes in a given context and version. |
| **Outcome signal** | Whether delivered memory helped, misled, was ignored, or required correction. Returns as new input. |
| **Context budget** | The explicit token or size limit within which output must fit. Returning nothing is a valid result. |
| **Harness** | The agent runtime or tool in which work happens. The Brain is harness-neutral. |
| **Lifecycle hook** | A harness event the Brain reacts to (equivalent to `SessionStart` and `UserPromptSubmit`) for proactive retrieval before the model reasons. |
| **MCP** | Model Context Protocol. Used for exploratory access, never as the only delivery path. |
| **Progressive disclosure (L0 / L1 / L2)** | L0: compact relevance signal. L1: navigational overview. L2: the full managed unit with supporting evidence, on demand. |
| **Unknown / CannotProve** | The meaning of an empty, filtered, or unavailable retrieval result. Never read as approval or as "no constraints apply." Distinct reason codes stay distinguishable when disclosure policy allows ([REQ-OUT-21](#req-out-21)). |
| **Reason-coded Unknown** | An unknown result that keeps a permission-safe reason such as `no_match`, `ambiguous_identity`, `source_not_connected`, `source_stale`, `source_unavailable`, `withheld_by_policy`, `retrieval_failed`, or `cannot_prove` ([REQ-OUT-21](#req-out-21)). |
| **Context Delivery Receipt** | The immutable, append-only record of exactly what a consumer was given on one retrieval: identities and authority, selected unit versions, grounding decisions, coverage, content digest, and usability window ([REQ-OUT-19](#req-out-19)). |
| **Coverage Manifest** | The per-source description of coverage and staleness that travels with every retrieval response and feeds grounding and fail-closed decisions ([REQ-OUT-20](#req-out-20)). |
| **Evidence Accessibility** | Whether the current consumer may inspect supporting evidence for a delivered claim, independent of whether provenance is known ([REQ-OUT-22](#req-out-22)). |
| **Fail closed** | When authoritative memory or policy cannot be retrieved or verified, an action that requires it stops rather than proceeds. |
| **Retrieval projection** | A derived index (vector, graph, full-text, relational) built from canonical memory. Never authoritative on its own. |
| **Reflector / Curator** | Processing roles: the Reflector extracts candidate lessons; the Curator links, deduplicates, and prepares them for admission. Neither is the executing agent. |
| **Observed work** | Work captured by watching the surface where it happens rather than by asking the person to describe it afterwards. |
| **Reconstruction** | The interpreted intent and ordered steps derived from observed-work evidence. Stored beside the evidence, linked step by step, reviewed by the observed person. |
| **Code graph** | A structure derived from repositories: symbols, call and dependency relations, ownership, version history. A source beside the code; never the authority over it. |
| **Portable memory format** | A documented, versioned, structured format used to import memory from or export it to other systems. Imports enter as candidates only. |
| **Scope deprecation** | Evidence that a scope or source is no longer valid. Weakens or expires every unit derived from it. |
| **Net value** | Outcome benefit of supplied memory minus its cost. Token savings alone are not net value. |
| **Research-agent baseline** | A from-scratch internal research agent used as the comparison arm for Brain-supplied context on a defined task class. |
| **Transcript pitfall review** | An output mode that reviews a full agent transcript and returns applicable lessons, known pitfalls, contradictions with memory, and policy conflicts. |
| **Agentic flow** | A place where a model decides something (capture, review, triage, detection, evaluation). Runs on the existing components; never writes shared memory directly. |
| **Decision lineage** | The linked chain Proposal → Decision → Execution → Outcome for one choice made during work ([REQ-PR-15](#req-pr-15)). |
| **Proposal / Decision / Execution / Outcome** | The four stages of decision lineage: what was suggested, what an authorized actor selected, what actually ran, and what was later observed. |
| **Exposure / influence / causal evidence** | Three levels of attribution: the unit was supplied; evidence shows it was used; a controlled comparison shows it changed the result. Only influence earns credit or blame, and only causal evidence supports a causal claim ([REQ-EV-06](#req-ev-06)). |
| **Verified outcome** | An Outcome judged by a named evaluator against an explicit acceptance criterion, with its uncertainty recorded ([REQ-ME-14](#req-me-14)). A successful execution alone is not a verified outcome. |
| **Retention / retrieval / grounding** | Three separate decisions: is it kept, may it be returned, and may it support a claim, recommendation, or action. The first two and a grounding ceiling are stored on the unit; grounding for a specific request is decided at read time ([REQ-ME-15](#req-me-15)). Stored does not mean grounding-authoritative. |
| **Autobiographical memory** | What the assistant itself said or believed: prior utterances, summaries, self-assessments. Kept for continuity; non-grounding until independent evidence supports it ([REQ-ME-17](#req-me-17)). Repetition is not corroboration. |
| **Grounding ceiling** | The most a unit may ever support (the highest purpose class) and the non-grounding uses it may serve; versioned on the unit. A per-request decision never exceeds it ([REQ-ME-16](#req-me-16)). |
| **Permitted-use label** | What a non-grounding unit may be used for in a request: `continuity`, `hypothesis`, `disputed`, `audit`, or `reflection` ([REQ-OUT-18](#req-out-18)). |
| **Shadow evaluation** | Running a candidate beside the active path on the same comparison basis and recording what it would have done, without letting it control or change anything ([REQ-EV-13](#req-ev-13), [REQ-EV-18](#req-ev-18)). |
| **Comparison basis** | What every shadow arm shares: task identity, authorization boundary, source snapshot, available evidence universe, external-state snapshot, and deterministic filters ([REQ-EV-14](#req-ev-14)). |
| **Protected task** | An owner-chosen task that a candidate must not get worse at. A regression on it blocks promotion whatever the average shows ([REQ-EV-17](#req-ev-17)). |
| **Continuity checkpoint** | The state a task needs to resume after session end, handoff, reset, or compaction: objective, done and pending work, open decisions, constraints, evidence, authority boundaries, next actions ([REQ-ME-20](#req-me-20)). Not durable memory ([REQ-ME-21](#req-me-21)). |
| **Compaction record** | The audit of one compaction: what was retained, removed, transformed, and left uncertain ([REQ-ME-23](#req-me-23)). |
| **Action journal** | The record of a task's irreversible or externally visible actions: intent and idempotency key before the action, result after it. Used on resume to avoid repeating or inventing actions ([REQ-ME-31](#req-me-31)). |
| **Recovery point** | The maximum task state, measured as checkpoint age, that may be lost on an abrupt end; set per task class ([REQ-ME-31](#req-me-31)). |
| **Memory maintenance** | Scheduled, threshold-triggered, and event-triggered checks that find stale, duplicate, contradictory, harmful, broken, or inconsistent memory and propose fixes ([REQ-ME-26](#req-me-26)). |
| **Low-risk maintenance action** | A reversible maintenance operation on an owner-approved list that may run without a per-case decision, such as rebuilding a stale projection ([REQ-ME-30](#req-me-30)). |
| **Maintenance proposal** | A suggested maintenance change with its trigger, evidence, and affected units, decided by an owner ([REQ-ME-28](#req-me-28)). |
| **Legal hold** | A governed instruction that keeps specified records unchanged and undeleted; it takes precedence over retention expiry and all maintenance ([REQ-ME-33](#req-me-33)). |
| **Expected version** | The version of a unit that a maintenance action or proposal was based on; the action commits only if that version is still current ([REQ-ME-32](#req-me-32)). |
| **Redirect** | What a merged-away or superseded unit becomes: a pointer to its successor that keeps its history, so references still resolve ([REQ-ME-35](#req-me-35)). |
| **Integrity attestation** | A signature or equivalent proof, bound to a managed identity and a record version, that shows who wrote a record and that it has not changed. It does not show that the claim is true ([REQ-SEC-16](#req-sec-16)). |
| **Trust root** | The organization-managed key or authority that integrity attestations are verified against; rotated, revocable, and audited ([REQ-SEC-18](#req-sec-18)). |
| **Historical trust chain** | The record of which keys and trust roots were valid when, with any compromise time, used to verify a record against the trust that applied when it was signed ([REQ-SEC-19](#req-sec-19)). |
| **Trusted timestamp** | A signing time from an organization-approved time source, bound to the attestation, that shows when a record was signed ([REQ-SEC-19](#req-sec-19)). |
| **Management dashboard** | The read-only visual view of users, memories, relations, statistics, net value, and health, filtered by the viewer's permissions. |
